## Engineering findings

Only offline CI is scheduled by repository events. There is no recurring rainfall or satellite refresh workflow. The national rainfall file is a dated snapshot from 23 November. Historical map layers represent 2022 observations.

The scoring feature validator rejects inputs available after issue time. It does not enforce how old forecast inputs may be, or whether the requested horizon has already expired at publication time. Historical evaluation needs to remain replayable, so a future live publishing wrapper should enforce freshness separately, record collection/run timestamps and mark overdue products stale.

The rain collector uses a common issue time after a batch of requests. It preserves each retrieval time but does not record the originating weather model initialization. Before automation, add batch-age checks, retained immutable snapshots, retry/recovery monitoring and a latest-success pointer that advances only after a complete validated batch. An earlier successful forecast must retain its original validity window when a refresh fails.

The M3 trainer enforces chronological partitions and unique evidence IDs across them. IDs alone cannot identify two records from the same flood episode. Before fitting real data, define episode grouping, temporal separation, representative negative windows and sampling weights where needed. Add reliability evaluation, event-level uncertainty, missed-event rate, false alarms and lead-time analysis. A calibration method being present does not establish calibrated operational probabilities.

## Proposed refresh policy

| Data/product | Initial policy | Purpose |
|---|---|---|
| Forecast rain and rolling 72-hour inputs | Every 6 hours, subject to provider availability and request budget | Capture revised forecasts well within the 72-hour horizon |
| Recent rainfall | Daily, respecting source latency | Update antecedent wetness and record whether inputs are estimates or observations |
| Radar scenes | Check daily and process newly available suitable acquisitions | Preserve actual observation time and age for every layer |
| Land cover, buildings and terrain | Check for new releases periodically; version and validate before adoption | Avoid pretending a static source gains new detail each week |
| Model parameters | Retrain after sufficient reviewed data or measured degradation, with held-out validation | Fresh inputs and model retraining have separate triggers |

These are proposed schedules. Weather model updates commonly occur every few hours, and an API response may combine model runs. [Open-Meteo update documentation](https://open-meteo.com/en/docs/model-updates)

A weekly forecast refresh leaves a four-day gap after a 72-hour horizon expires. More frequent refreshes improve timeliness. Accuracy still depends on model skill, input quality, spatial coverage and valid outcome evidence.
